# Plan 4, Part 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the app its final shape (fan picker, upside-down reversed cards, desktop layout, Ask "Coming soon", in-app Terms/Privacy edited in the portal, no exits to the landing site) and let readers exist (invite or role offer, guidelines, private log), with two wording-safety fixes.

**Architecture:** Builds on the existing monorepo. Wording safety and the new "document" format live in `@astro/copy`; legal pages are three new published-text kinds served by the app and edited in the portal with a Tiptap 3 editor that converts to the checked format in the browser. Reader roles move to their own table, written only by checked database functions (like `accept_invite`); the reader's log is an app-only table that the portal's database user can't touch.

**Tech Stack:** Turborepo + pnpm, Next.js 16 on OpenNext Cloudflare (Workers Free), Neon Postgres via Hyperdrive, Drizzle, Better Auth, Zod 4, Vitest, Playwright, GSAP 3 (app), Tiptap 3 (portal).

**Spec:** `docs/spec/2026-11-27-plan4-part1-design.md` (approved 27 Nov). Mockups: https://claude.ai/artifact/BFRgaSVWbDGULjyxKX9gC9, page "Ask, readers, desktop (27 Nov)" — artboards named below by file (`project/P4-*.dc.html`).

## Global Constraints

- Workers Free: 10 ms CPU per request; each Worker's upload under the Free size limit (check with `wrangler deploy --dry-run`). The Tiptap editor loads only on the portal's Legal tab.
- Every permission is checked on the server; reader roles are written only by checked SQL functions or the portal's role service; the app's database user never writes role tables directly.
- No HTML is ever stored or rendered from editable text; documents render as React elements.
- Every new visible string is a catalogue entry (editable in the Text screen); defaults are the mockups' wording.
- Phone layout below 1024 px (bottom tabs); desktop at ≥ 1024 px (side menu, max width ~1100 px).
- Reduce Motion: no fan-out animation, no sliding, crossfade instead of flips.
- Touch targets ≥ 44 px; keyboard and screen reader support for picker, editor and log.
- The app never links to `astro.midnightpoetry.studio` (landing → app links are fine).
- Reader's log: visible only to its reader with an active reader role; never in the portal, AI, audit summaries or support tools; promise wording "Private to you. Astro staff can't see it in the app or portal."
- Delivery: branch `feat/plan4-part1`, one pull request; merge only when the owner says "merge". Deployment steps stay browser-only.

## Review Focus

1. A reader role reaching someone by any path other than the two checked accept functions or the owner's self-add (admin giving a staff member the role, the app writing `reader_role`, an offer accepted by the wrong account) — Tasks 9, 10.
2. Reading or changing another reader's log entry by id, or after one's reader role was removed — Task 12.
3. A legal document carrying a `javascript:`/`data:` link, an oversized or deeply wrong JSON body, or pasted HTML — Tasks 2, 4.
4. The fan picker on a 320 px-wide phone and with the 22-card Majors fan; a finger that lifts outside the fan — Task 6.
5. The guidelines republished between a reader opening the accept screen and pressing Accept — Task 11.
